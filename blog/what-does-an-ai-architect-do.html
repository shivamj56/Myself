What does an AI architect actually do? Five decisions from building NexeraAI and Clonix

By Shivam Anil Jha · AI architect & full-stack developer, Mumbai · 17 November 2026

“AI architect” gets used for everything from writing prompts to running a research team. In my work it means something narrower: deciding how a product uses AI models it doesn't train, and building the app so those decisions hold up when real people use it. The model is one part. The rest is where the data comes from, what the app does when the model fails, and how anyone can tell an answer is right.

Here are five decisions I made in two of my products: NexeraAI, an AI career platform, and Clonix, a Chrome extension that turns a website into design tokens for AI code editors. Each one is the kind of call an AI architect is there to make.

1. Decide where AI doesn't go

The first decision is often to leave AI out of a step. In Clonix, turning a scanned page into design tokens and editor rules is plain code, with no network call and no model. The same scan always gives the same files, so they can be tested, compared and trusted. AI comes in at exactly one step: turning a section of the page into a component, where judgment helps and there is no single right answer.

NexeraAI follows the same idea. A job's skills come from a dictionary match first, and an optional AI pass refines them later. The cheap, predictable path runs every time, and the model adds to it instead of replacing it.

2. Ground the model in real data

A model only knows what you give it. NexeraAI's assistant gets today's date, recent web results when they help, and the open roles on NexeraAI that fit the question. Its instructions say to recommend only from that list, by exact title, and never to invent a role.

That moves most of the work into the data. NexeraAI has an importer for RemoteOK, Arbeitnow and the public job boards companies run on Greenhouse, Lever and Ashby, one normaliser for every source, and a SHA-1 check on the title, company and location, so the same job posted on five boards shows up once.

Clonix does the same for design. It doesn't ask a model what a site looks like. It measures the page in your browser: computed styles, loaded fonts, and only the elements a visitor can actually see, within a budget of 6,000 elements in 300 ms. Anything it doesn't reach is counted and reported, never guessed.

3. Put several providers behind one door

Every AI feature in NexeraAI goes through one small client. Groq, Google Gemini and OpenAI accept the same chat-completions format, so one code path serves all three. The client tries the providers that have a key in order (Groq with Llama 3.3 70B first, then Gemini, then OpenAI), retries once on a rate limit or a server error, and then moves on to the next. An outage, a price change or a better model becomes a configuration change, not a rewrite.

4. Ask for structure, then check it

Free text is hard to build a product on. Each NexeraAI feature asks the model for one JSON object with fixed keys. The résumé analysis returns a score from 0 to 100, an ATS score, the skills it found, strengths, specific improvements and a short summary. Models sometimes wrap JSON in code fences or add a sentence before it, so a small function strips that and takes the outermost object before parsing. If it still doesn't parse, the error says so.

Clonix applies the same thinking to what it hands an editor. Its design brief is written as rules, not suggestions: use the tokens exactly and never approximate, use only the site's breakpoints, and switch dark mode with the site's own selector. The clearer the contract, the less the model has to guess.

5. Decide what happens when the AI fails

This is the decision I care about most. In NexeraAI, if every provider fails, the client raises a clear error. It never returns sample data. A made-up résumé score is worse than no score, because people act on it. A scanned résumé is only a picture of text, so NexeraAI says that plainly and asks for a text PDF instead of guessing.

The same habit outside AI

Orbit OS, my Google TV app, has no AI in it, but it runs on the same rule: design the failure path first. Before it changes anything, it records how the TV is set up. It switches apps off instead of uninstalling them, writing each one down as soon as Android confirms it, so one tap of Undo brings the TV back. “What happens when this goes wrong?” is the same question either way.

AI architect, AI engineer, ML engineer

The titles overlap, and companies use them differently. As I use them, an ML engineer trains and tunes models, and an AI engineer builds features on top of them. An AI architect decides how the whole product uses them: which models, fed with what data, under which rules, and what happens when they fail. Then they make sure the rest of the system can carry those choices. On a small team, one person often does all three.

If you're adding AI to a product

Start with the data and the failure path, not the prompt. Decide where AI isn't needed. Put your providers behind one client, ask for structured output, and make the app say so when the model can't answer. Those five decisions do more for a product than any single prompt.
